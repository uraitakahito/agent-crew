# 提案の依頼: 見本の題

Technical Program Manager（TPM 役）から Software Engineer 役への依頼です。

- 依頼の種類: **提案**（案を出して比べる。まだ作らない）
- 作業項目: #1
- 返答と報告: 日本語
- 知らせの名乗り（--from）: 「#1 提案」

## 何を

- 見本の題 について、案を 3 つ出して比べ、推しを 1 つ（理由つきで）言う。決めるのは Product Manager。

## やること

- 案ごとに、何が変わるか（場所と数・前後の例）・手間（PR の本数・リリース）・良い点と悪い点・危うい所・確かめ方を書き、比べる表を置く。
- 推しの理由と、Product Manager に決めてほしいこと（番号つき・既定の答えつき）を書く。
- 手で試すのは、費用が掛からず・外のアカウントに触れず・動いている共有の物に触れない物だけ。試した物と試していない物を分けて書く。

## 案を出す前に

- 同じ話が、もう決着・見送り・未決になっていないかを記録で確かめる。済んでいる話を出し直さない。
- 自分たちの仕様や決まりを、動かせない制約として書かない（動かせないのは、外の仕様と読み手の動きだけ）。

## 範囲

- この依頼では、機能のコードを変えない。変えてよいのは、下の「docs とコメントの食い違い」の直しと、作業項目の状態だけ。

## 作業項目の状態

- 作業項目は #1（GitHub Issues）。着手するときに進行中にし、打った後に読み直して変わったことを確かめる。親の作業項目や段ごとの作業項目が在れば、同じく動かす（すでにそうなら読み直すだけ）。
- 完了にする前に、結果（PR・版・CI の run）をコメントに書き、閉じた後に読み直す。親は閉じる条件に照らし、満たさなければ開けたまま理由を書く。

## 結果のまとめ方

- 結果は HTML の Artifact にまとめる。冒頭に 30 秒で読める結論を置き、比べる所は表、込み入った所は図にする（図は inline SVG で、ライトとダークの両方で読めるように）。公開の前に、電話の幅でもはみ出さないかを手元で確かめる。
- 主張はコードか docs で確かめてから書き、根拠（ファイルと行・打った命令・外の資料は公式の URL と確かめた日）を添える。確かめていない物は「確かめていない」、決まっていない物は「決まっていない」と書き、推し量って埋めない。
- 「サーバ」「ページ」のような汎用語で立場を書かない。正体の名前で書く。略語は初出で展開する。

## 開く場所

- 公開した Artifact は、TPM 役の workspace と自分の workspace の両方で開く: TPM 役の側は `cmux open <URL> --workspace <TPM 役の UUID>`、自分の側は `cmux open <URL>`。両方の出力に `OK urls=1` が出たことを確かめ、報告に書く。

## 後方互換

- 後方互換性と移行期間は考えなくてよい（使っているのは自分たちだけ）。古い形を残すための分岐は作らない。

## 共有の開発環境

- 共有の開発環境（コンテナ・共有の開発環境）の状態を変える操作は、自分で打たない。
- 頼むときは DevOps 役（workspace:2）に、段の番号・打つ命令（そのまま）・起こす物と止める物（名前と port）・見込みの時間・終わった後に元へ戻すか、の 5 つを書いて送る。1 つずつ頼む。
- 返事（承認・待て・やり方の変更）を受けるまで、その操作をしない。打つのが DevOps 役か自分かは、返事で決まる。予定に無い操作が要ったら、打つ前に一言頼む。終わったら、元に戻したかを含めて報告する。
- 待つ間は、待ちの印を立てる: `cmux set-status wait "<何を待つか>" --workspace <自分の workspace> --icon hourglass`。返事を受けたら消す: `cmux clear-status wait --workspace <自分の workspace>`。待つ間に進められる物（ほかの段・docs の直し・PR の本文）を進める。
- 読むだけの操作（一覧・ログ・状態を見る・SELECT・GET）は、頼まずにしてよい。

## Product Manager への問い合わせ

- 判断が要る所が出たら、止めて訊く。推し量って進めない。
- 訊くときは、中身（何を・どこで・何が出れば良いか・返事の形）を書いた HTML の Artifact を作り、TPM 役の workspace と自分の workspace で開く。そのうえで TPM 役に「【利用者への依頼】」で始まる知らせで URL と要点を送る。答えは TPM 役から「【利用者の答え】」で届く。目で確かめてもらう物は、数分で済むよう見る所を絞る。答えが届いたら直して、同じ URL で出し直す。
- Product Manager に打ってもらう命令は、貼っても折り返さない短い 1 行にする。
- 待つ間は、利用者の判断待ちの印を立てる: `cmux set-status user-wait "<何を待つか>" --workspace <自分の workspace> --icon hourglass`（返事を受けたら消す）。

## docs とコメントの食い違い

- 見つけた docs とコメントの食い違いは、お勧めの内容で直して PR で入れてよい（確認は要らない）。直しは docs とコメントだけの PR にし、機能の PR に混ぜない。ただし、機能の段で触るファイルのコメントは、その段で一緒に直してよい。
- docs とコードが食い違うときは、コードに従う。コードの方が誤りなら、docs の直しに入れず、計画の段か作業項目に回す。
- 直しの計画と結果は、作業項目のコメントに書く。直した PR と、直さずに登録した物の両方を、最後の報告に挙げる。

## このプロジェクトの決まり

- （見本）プロジェクトに固有の決まりは、profile の `partials/project-rules.md` に書く。repo には見本だけを置く。

## 終わったら

- 自分の画面で報告する: Artifact の URL／要点（3〜5 行。提案なら案ごとに 1〜2 行と推しと理由）／作業項目の状態／2 つの workspace で開いた結果／見つけた食い違い。
- TPM 役（workspace:1）にも知らせる: `cmux agent message <宛先> --from "<自分の名前>" -- "<文>"`
